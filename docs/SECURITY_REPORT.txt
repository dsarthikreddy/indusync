SARTHIK ROOM v4 - SECURITY REPORT
=================================
Scope: website 2_Website_v4 (Python FastAPI - NOT Flask; the old Flask prototype is no longer used) and door board v8.1.
No system is "unhackable". This report lists what was checked, what changed and what risk remains.

A. RISKS FOUND BEFORE (v3)
  1. Passwords: PBKDF2-SHA256 240k rounds (below today's advice).        2. No idle timeout (stolen cookie valid 30 days).
  3. Page security policy allowed ANY inline script (weak XSS defence).   4. Unhandled errors / bad input could show internals;
     one upload error printed the Python error text.                     5. Rate limits only on login.
  6. No security log.  7. No backups.  8. Secrets (Wi-Fi password, door key, phone channel) inside the firmware source.
  9. Door board v8: network work inside the door loop (slowed phone key / QR) - fixed in v8.1.
  Already good in v3 (kept): random 256-bit login tokens stored only as hashes, HttpOnly + SameSite=Lax cookies (Secure on
  HTTPS), wrong-password lockout, CSRF header + same-origin check, admin/viewer roles checked on the server, parameterised
  SQL, safe file names for photos (strict pattern, no user paths), private folders not served.

B. WHAT CHANGED
  - scrypt password hashing (memory-hard); old passwords upgrade automatically at next sign-in; same timing for unknown users.
  - Sessions: idle timeout 2 h (normal) / 14 days (remember me); new session id at every sign-in; sign-out ends it on the server.
  - Pages get a new random script nonce on every load; injected scripts are blocked (no 'unsafe-inline' for scripts).
  - Generic error pages/messages for 400-500; crash details never reach the browser.
  - Rate limits: button presses 180/min per internet client, uploads 20/min, door commands 20/min, messages 30/min,
    phone messages 10/min, backups 3 per 5 min. Internet clients with 40 refused requests in 5 min are paused 10 min.
  - Security log data\security.log (rotating): sign-ins, failures, lockouts, CSRF blocks, refusals, every admin action.
    Never stores passwords, cookies, tokens or photos.
  - Uploads: size checked BEFORE receiving (12 MB), real content must be JPG/PNG/WebP, decoded and never stored as a file
    (only the 512-number face code is kept), strict person ids.
  - Door commands from the website: admin only, whitelist on the website AND on the board, secret door key, logged.
  - Backups: daily automatic + "Back up now"; folder outside the website; Backup to USB.bat for an offline copy.
  - Firmware v8.1: secrets moved to secrets.h (+ .gitignore); website door commands need DOOR_API_KEY.
  - Minimum library versions raised; pip-audit: no known vulnerabilities in the tested versions.

C. FILES CHANGED (website): cctv/auth.py, main.py, db.py, facewatch.py, detector.py, settings_store.py, web/*.html,
   new: cctv/secure.py, cctv/integrations.py, SARTHIK Room.vbs, tools/*.ps1, Turn On/Off Autostart.bat,
   Stop SARTHIK Room.bat, Backup to USB.bat, .gitignore, requirements.txt.   Firmware: classync_stage1_v8_1.ino + secrets.h.

D. ACTIVE CONTROLS: sign-in required for every page/API/photo (server-side), admin-only actions, default deny,
   CSRF protection, nonce CSP, frame blocking, nosniff, no-referrer, permissions policy, HSTS on HTTPS,
   rate limits, abuse pause, lockout, idle timeout, security log, safe uploads, path-traversal checks, backups.

E. YOU MUST DO
  1. Use a long admin password (12+ characters).          2. Make Viewer accounts for family, not admins.
  3. Public link only through Tailscale Funnel (HTTPS). Never open port 8000 on your router.
  4. Copy backups to a USB drive weekly and unplug it.     5. Keep Windows updated; run Install.bat again monthly.

F. SECRETS TO CHANGE if these files were EVER posted publicly (GitHub, Drive, WhatsApp groups):
  - Wi-Fi password of "ACT" (it is in old sketches such as cam_face_test.ino and in secrets.h).
  - QR_SECRET (v6 firmware) = SECRET_KEY (make_pass.py): change BOTH to the same new text; old passes stop working.
  - DOOR_API_KEY (secrets.h) = Door key (website Control page).   - ntfy channel name (anyone who knows it can read alerts).

G. REMAINING RISKS
  - Inline STYLES are still allowed (needed by the existing design); scripts are protected.
  - On plain http (laptop/home Wi-Fi) the cookie cannot be "Secure"; use the https Tailscale link outside home.
  - The door board's own web API is unencrypted on your home Wi-Fi (key protected, read-only data is open on the LAN).
  - ntfy topics are public by name; keep the name secret.   - All signed-in family members share one household view
    (no per-person photo albums), by design.   - The laptop is a single point: if it is stolen, the data is on it.

H. CHECKLIST BEFORE PUBLISHING THE LINK
  [ ] Admin password strong   [ ] Others are Viewers   [ ] Public link = https://...ts.net   [ ] Port 8000 not forwarded
  [ ] Backup made and copied to USB   [ ] Logs page shows no unknown sign-ins   [ ] Door key changed from the default

==================== STAGE 3 (cloud) ADDITIONS ====================
- Firestore rules = the only security layer on the free plan: default deny; members list by e-mail;
  roles admin / viewer / device / reporter; events create-once (retry must be identical), never edited
  or deleted; commands admin-only, board may only mark them done; one-time first-admin bootstrap;
  nobody can change their own role; private chats readable only by the two people.
- Website: every value HTML-escaped (XSS test passed), strict Content-Security-Policy, HSTS, no framing.
- Live "Run security check" on the Health page tests the deployed rules against the real database.
- Board: only whitelisted commands from the cloud; Telegram commands accepted only from the owner chat.
- Sheet web address protected by a 128-bit random key; door events copied by the laptop are ignored.
- n8n listens only on 127.0.0.1. Secrets live only in secrets.h, tools\stage3_state.json, n8n.env and
  the Sheet's hidden Script Properties - never in the website files.
- After setup: untick "Enable create (sign-up)" in Firebase Authentication.
- Known limit: the board's HTTPS does not verify certificates (setInsecure); data access still needs
  the board's own login.
